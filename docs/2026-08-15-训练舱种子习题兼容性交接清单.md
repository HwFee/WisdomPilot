# 训练舱种子习题 · 兼容性交接清单

> 日期：2026-08-15
> 来源：多轮多智能体全量审核（7 + 5 + 2 代理，执行级实测）结论
> 用途：供另一位 AI 据此修复训练舱「种子习题 ↔ 判题系统」之间的兼容性问题。
> **重点**：本文只列**系统兼容性**问题；「题目本身」（题干/答案/缺陷标注/测试用例数据）已全部修复完毕，无需重复处理。

## 一、背景

训练舱种子数据（[backend/app/training/seed.py](backend/app/training/seed.py)）新增了 **30 个代码审查关卡 + 20 个竞技场挑战 + 5 场认证考试 29 题**。判题逻辑在 [backend/app/training/service.py](backend/app/training/service.py)。多轮审核确认：**题目数据本身的正确性已达标**（详见第三节），剩余问题全部集中在「判题降级链路」「已有库升级」「前端 mock 同步」「显示文案」四个系统层面。

## 二、待修问题（按严重度）

### 🔴 P0 · 竞技场降级判题缺口

**问题**：新增的 15 个竞技场挑战（DEBUG-0096 ~ DEBUG-0110）只有 Judge0 真判题路径，**没有关键字匹配降级**。

- 降级表 `ARENA_JUDGES` 只注册了 DEBUG-0091 ~ 0095（[service.py:1360](backend/app/training/service.py:1360)）。
- `judge_arena_code` 对未知挑战 ID 直接返回 `passed=0, total=0, solved=False`（[service.py:1368](backend/app/training/service.py:1368) 附近）。
- `judge_arena_code_submit` 在 Judge0 未配置 / 调用异常时回退到 `judge_arena_code`（[service.py:1648](backend/app/training/service.py:1648)）。
- 影响：**Judge0 未启动的开发环境下，这 15 个新挑战永远判失败、无法攻克**，还会以「未攻克」身份进入复盘队列。破坏设计注释承诺的「没启动 Judge0 的开发环境功能完全可用」（service.py:1376 附近、.env.example:38-42）。

**修复建议（二选一）**：
1. 为 DEBUG-0096 ~ 0110 各补一个关键字判定函数（照 `_judge_debug_0091` 的模式：检测修复模式子串，返回 passed/total），并注册进 `ARENA_JUDGES`；或
2. Judge0 未配置时，把这 15 关从每日轮换池（[router.py:397](backend/app/training/router.py:397) 附近）剔除，并在启动日志/文档说明「新挑战依赖 Judge0」。

### 🟠 P1 · 认证 code 题降级判定形同虚设

**问题**：`judge_cert_answer` 的 code 分支判定规则是「去掉空白后包含全部 `answer_includes` 片段」（[service.py:2308](backend/app/training/service.py:2308)）。但 **7 道 code 题的 `answer_includes` 只有 `["return"]`**（几乎任何代码都满足）：

| 位置 | 片段 |
|---|---|
| placement:p4（[seed.py:1723](backend/app/training/seed.py:1723)） | `["return"]` |
| cert-recursion:q5（[seed.py:1749](backend/app/training/seed.py:1749)） | `["return"]` |
| cert-recursion:q6（[seed.py:1756](backend/app/training/seed.py:1756)） | `["return"]` |
| cert-sorting:q5（[seed.py:1772](backend/app/training/seed.py:1772)） | `["return"]` |
| cert-sorting:q6（[seed.py:1779](backend/app/training/seed.py:1779)） | `["return"]` |
| cert-linkedlist:q5（[seed.py:1796](backend/app/training/seed.py:1796)） | `["return"]` |
| cert-linkedlist:q6（[seed.py:1803](backend/app/training/seed.py:1803)） | `["return"]` |

另有 placement:p5 = `["n>0"]`（[seed.py:1723](backend/app/training/seed.py:1723) 附近）、cert-pointer:q6 = `["NULL"]`，同样偏弱。

- 影响：Judge0 不可用时，提交 `def quicksort(arr): return arr` 这类错误代码即可判对，认证可信度失效。
- 判别力正常的只有 cert-pointer q5（`["*a=*b","*b="]`）、q6（`["NULL"]`）。

**修复建议**：给每道 code 题补**算法特有**的关键片段（如 quicksort 判 `arr[i] < pivot`、merge 判 `merge(left,right)`、reverse 判 `s[::-1]` 或递归骨架），或明确这些题强制依赖 Judge0、无 Judge0 时不出题。

### 🟠 P1 · 已有部署静默缺内容

- 影响：已有数据库升级后**静默缺失**新增的 30 关 / 20 挑战 / 29 题，用户无感知。

**修复建议**：在 `docs/backend-api/README.md` 迁移表、根 README、以及 lifespan 启动日志补「已有库需先跑 `python -m scripts.migrate_backfill_deck_content`」提示（脚本已实测可用：30 关/63 缺陷/20 挑战/5 考试/29 题全部回填成功且幂等）。

### 🟡 P2 · 竞技场 failing_output 叙述与实际不符（显示文案）

**问题**：`failing_output` 是展示给用户的调试线索，但多处与真实缺陷代码在真实 test_cases 上的表现不一致（不影响 Judge0 判分，但误导用户）：

| 挑战 | 叙述声称 | 实际（实测） |
|---|---|---|
| DEBUG-0091 | 偶数用例 TIMEOUT / 疑似死循环 | 无死循环（`while lo > mid-1` 只跑 1 次），返回**错误值** 3.5/-2.5/6.5 |
| DEBUG-0092 | test_last_element IndexError、test_empty PASSED | 空数组才 IndexError，末元素用例通过（归属互换） |
| DEBUG-0097 | 1 passed, 4 failed | 3 passed, 2 failed |
| DEBUG-0099 | 1 passed, 4 failed | 3 passed, 2 failed |
| DEBUG-0100 | 3 passed, 2 failed，含空串用例 | 2 passed, 3 failed，无空串用例 |
| DEBUG-0110 | 2 passed, 3 failed | 1 passed, 4 failed |
| DEBUG-0108 | 「执行超过 5s」/ 15.40s | Judge0 CPU 上限固定 10s（见下条） |

**修复建议**：按上表真实行为重写对应 `failing_output`；DEBUG-0091 代码内注释「没有退出条件 lo 会一直减下去」也是错的，一并修正。

### 🟡 P2 · `time_limit_sec` 字段从未被判题链路使用

**问题**：[seed.py:952](backend/app/training/seed.py) 注释宣称 `time_limit_sec` 是判题时间上限，但该字段在判题链路（`judge_arena_code_submit` → `execute_batch`）中**从未被读取**；Judge0 一律按全局固定值 `JUDGE0_CPU_TIME_LIMIT_SECONDS = 10` 执行（[judge0_client.py:30](backend/app/services/judge0_client.py:30)、[judge0_client.py:114](backend/app/services/judge0_client.py:114)）。

**修复建议**：要么把 `time_limit_sec` 透传给 Judge0（按挑战差异化限时），要么移除该字段并修正注释/前端展示，避免误导。
