> 权威实现：`backend/app/deck/`（mastery.py / service.py / router.py / models.py / seed.py）
> 接口规格：`docs/backend-api/01-target-design.md` §3/§5/§6/§7/§8
> 设计依据调研：`docs/2026-07-26-知识追踪与AI导师调研.md`

## 0. 一句话总览

**一切学习行为落成事件（`deck_mastery_events`），事件流经纯函数引擎重算出掌握度缓存（`deck_user_mastery.p_l/level`），缓存驱动能力图谱、弱点清单、主任务分发与导师上下文，导师的费曼检验又产生新的事件——闭环。**

```
行为层      review-gym 命中   定级测试   费曼检验   认证小测   (arena 未接)
              │                │           │          │
              ▼                ▼           ▼          ▼
事实源   ┌──────────────── deck_mastery_events ────────────────┐
         │ (user_id, kp_id, created_at, source, correct,      │
         │  grade, hints_used, latency_ms)                    │
         └──────────────────────┬─────────────────────────────┘
                                ▼ 重算（纯函数，无 DB）
引擎层   mastery.py: recall_probability / mastery_level / compute_trend / feynman_grade
                                ▼ 落库
缓存层   deck_user_mastery (p_l = 当前回忆概率, level = 初识/熟悉/熟练/精通)
                                ▼
消费层   能力图谱 · 弱点清单 · 今日主任务 · 导师建议主题 · 复盘队列 · 导师即时反馈
                                ▼
回写层   费曼 verdict → 新事件 → 回到事实源（闭环）
```

核心纪律：**事件表是事实源，`p_l/level` 只是缓存读模型；任何模块不得直接改 `p_l`，只能写事件后重算。**（旧系统的固定 delta 直改已随 BKT 一起废弃。）

## 1. 采集层：五类事件源

| 来源 source | 触发点 | 记什么 | 实现位置 |
|---|---|---|---|
| `review_gym` | 审查关提交/重做结算 | 该关 `related_weakness` 绑定的知识点，每**新增**一处命中记一条 `correct=true` 事件（幂等，重做只按新增命中结算） | `router.py` `_record_review_mastery`（~568）、提交 ~640 / 重做 ~673 |
| `placement` | 定级测试交卷 | 每个知识点一条事件，`correct = 得分 ≥ 60`（`PLACEMENT_PASS_SCORE`），解决能力图谱冷启动 | `router.py` 定级端点 |
| `feynman` | 「考考我」提交解释 | `correct = grade != '待加强'`，`grade` 原样记录 | `router.py` `/api/tutor/feynman/check` |
| `certification` | 认证小测 | 按通过情况记事件 | `router.py` 认证端点 |
| `arena` | 调试竞技场 | **未接入**——挑战数据模型无知识点关联字段，见 §7 缺口 | — |

事件字段里 `hints_used` 目前**只记录、不进公式**（预留给"提示依赖度"负向信号）；`latency_ms` 同理备用。

## 2. 引擎层：`backend/app/deck/mastery.py`（纯函数，无 DB 依赖）

所有阈值都是模块常量；对应测试 `backend/tests/test_deck_mastery.py`（35 用例）。

### 2.1 回忆概率（HLR，半衰期回归）

```
p = 2^(−Δ/h)
```

- `h`（半衰期，天）：初始 1.0；每答对一次 `h = min(h×1.8, 180)`；每答错一次 `h = max(h×0.5, 0.2)`。通过重放该 (user, kp) 的全部事件得到。
- `Δ`：距**最近一次答对**事件的天数；从未答对过则取距首次事件的天数 +1。
- 性质：答对后 p≈1 并随时间自然衰减（**BKT 做不到的遗忘建模**）；答错收缩 h，使后续衰减更快。

### 2.2 掌握等级状态机（Khan 式透明四档）

| 等级 | 条件 |
|---|---|
| 初识 | 无事件，或 p < 0.3 |
| 熟悉 | p ≥ 0.3 |
| 熟练 | p ≥ 0.6 且答对 ≥ 3 次 |
| 精通 | p ≥ 0.8 且答对 ≥ 4 次 **且** 存在间隔 ≥ 3 天的两次答对（抗遗忘证据）**且** 至少一次答对来自实战源（`review_gym`/`arena`/`certification`） |

**关键门控：只靠费曼「讲清楚」永远到不了精通。** 解释质量是佐证信号（LLM 评分有冗长偏置等已知可靠性问题），必须实战 corroborate。

### 2.3 趋势 `compute_trend`

用 7 天前的事件子集重算当时的 p，与当前 p 比较：差 > +0.02 为 `up`，< −0.02 为 `down`，否则 `flat`。因含遗忘衰减，长期不练会诚实显示 `down`。（此前实现硬编码 `"flat"`。）

### 2.4 费曼量规评分 `feynman_grade`

- 每个知识点在种子数据带 3–5 个 `key_points`（label + 同义词组），见 `seed.py`。
- 覆盖率 = 命中的要点数 / 总要点数；文本含因果标记（因为/所以/否则/如果）与例证标记（比如/例如/假设/当）给结构加成。
- 评级：覆盖 ≥80% 且有结构 → **优秀**；覆盖 ≥50%，或 ≥1/3 且有结构 → **良好**；否则 **待加强**。
- 反馈文案 `feynman_feedback(grade, covered, missed)` **点名遗漏要点**，不是泛泛点评。
- 接 LLM 后此函数作为 LLM-as-judge 的 rubric 锚点，接口不变。

## 3. 缓存层：`deck_user_mastery`

`(user_id, kp_id, p_l, level, updated_at)`。唯一写入口是 `service.py` 的 `record_mastery_event()`：插事件 → 拉取该 (user, kp) 全部事件 → 调引擎重算 → upsert 缓存，返回 `(p_l_before, p_l_after, level)` 供响应即时反馈。

## 4. 消费层：掌握度驱动什么

| 消费方 | 用法 | 位置 |
|---|---|---|
| 能力图谱 `/api/ability-map` | 返回每个知识点的 `p_l` + `level` + 真实 `trend`；三轴 `weakest_focus` = 该轴 p_l 最低的知识点 | `router.py` ability-map 端点、`service.py` ~62-79 |
| 仪表盘弱点清单 | 全库 p_l 最低的若干知识点 | `router.py` ~298-307 |
| 今日主任务 `build_main_task` | 最弱知识点 → 导师任务；最低能力轴 → 对应模块任务；认证冷却期判断 | `router.py` ~205-230 |
| 导师建议主题 `suggested_topics` | p_l 最低的 3 个知识点（`_weakest_kp_names`） | `router.py` ~160、~904 |
| 复盘队列 `/review` | 低 p_l 知识点生成 `kind='knowledge'` 复盘项，入口 `/tutor?topic=` | `router.py` ~762-773 |
| 导师即时反馈 | 费曼 check 响应携带 `mastery_update: {kp_name, p_l_before, p_l_after, level}`，前端展示「掌握度 42%→57%」 | 契约 `frontend/lib/api/deck/types.ts`；UI `components/tutor/TutorClient.tsx` |

## 5. 回写层与导师会话闭环

1. `POST /api/tutor/feynman {topic}`：按**精确知识点名**解析 kp，创建服务端会话，返回 `feynman_session_id` + 开场追问。（已废弃旧的子串匹配 `name in text`。）
2. 用户输入解释 → `POST /api/tutor/feynman/check {session_id, text}`：从会话取 kp（未知/他人会话 404），量规评分 → 写 `feynman` 事件 → 重算缓存 → 响应带 `grade` + `mastery_update`。
3. 缓存变化即刻被 §4 所有消费方读到：能力图谱变色、弱点清单重排、次日主任务换题。

这就是"对话有后果"的完整链路：**失败史（事件）→ 导师追问（建议主题/复盘入口）→ 解释检验（量规）→ 掌握度更新（事件+缓存）→ 训练分发变化。**

## 6. 护栏与设计原则

- **不给答案是产品规则，不是 prompt 建议**：导师回复逻辑固化在 service 层；接 LLM 后提示升级阶梯封顶在"部分脚手架"，永不输出可直接运行的修复代码。实证依据：Bastani et al. PNAS 2025——无护栏 AI 辅导使独立考试成绩 −17%。
- **讲清楚 ≠ 会了**：精通必须实战 corroborate（§2.2）。
- **遗忘是一等公民**：HLR 天然衰减，趋势会诚实地往下走，驱动复盘队列。
- **可解释性优先**：四档等级 + 回忆概率用户看得懂；刻意不用深度 KT（AKT/DKT 需 10 万+交互且不可解释）。

## 7. 已知缺口（后续工作）

1. **arena 未接掌握度**：`DeckArenaChallenge` 无知识点关联字段。要接需给 challenge 加 kp 映射，然后按判题结果写 `arena` 事件——接上后精通门控的实战源才完整。
2. **定级初值偏高**：placement 答对即 p≈1.0（Δ≈0 的 HLR 语义），随后自然衰减。若产品希望定级后初始掌握更保守，可给 placement 事件单独的先验 h。
3. **导师上下文注入尚未到 LLM**：目前追问/点评是脚本化 + 量规规则版；弱点的个性化已体现在建议主题与复盘入口，但"引用你昨天的具体失败"要等 LLM 接入后在 service 层注入事件史。
4. **费曼会话在内存中**（`FEYNMAN_SESSIONS` dict）：服务重启丢会话，多实例部署不共享。上量前需落库或 Redis。
5. **`hints_used` 未进公式**：提示依赖度作为负向信号的权重待有数据后标定。
