## 一、代码修改记录

### 1. 登录契约精简：前端发 email，后端只查邮箱，用户名可重复

**背景**：原 `UserLogin` 同时支持 `username`/`email` 两个字段，前端却只发 `username`（把邮箱塞进 username 字段），后端靠 OR 查询 + model_validator 兼容两种客户端。实际只有一个前端，这套兼容机制成了死代码。

**改动**：

| 文件 | 改动 |
|---|---|
| `backend/app/auth/schemas.py` | `UserLogin` 改为 `email: EmailStr`（必填）+ `password` + `remember_me`；删除 `username` 字段与 `set_login_identifier` validator |
| `backend/app/auth/service.py` | `login()` 只按 `User.email` 查（`scalar_one_or_none`）；`register()` 只查邮箱重复，删除用户名冲突分支 |
| `backend/app/auth/models.py` | `username` 去掉 `unique=True`，保留 `index=True`（用户名仅作展示昵称） |
| `backend/app/auth/errors.py` / `router.py` / `__init__.py` | 删除死代码 `UsernameAlreadyRegisteredError`（含常量、导出、except 分支） |
| `backend/scripts/migrate_drop_username_unique.py` | 新迁移脚本：`data.db` 的 `ix_users_username` 由 UNIQUE 改为普通索引（已执行） |
| `frontend/lib/api/auth.ts` / `types/api.ts` | `login()` 与 `UserLogin` 类型改发 `email` 字段 |

**要点**：唯一性检查从"代码层 OR 查询"收口到"数据库唯一索引 + 按 email 单查"，语义更清晰；`data.db` 的 email 唯一索引（`ix_users_email`）保持不变。

### 2. Pylance 类型警告：scalars().first() 推断链

**问题**：`existing_user = result.scalars().first()` 的返回类型依赖 SQLAlchemy 泛型链一路推断（`Select[tuple[User]]` → `Result[tuple[User]]` → `ScalarResult[User]` → `User | None`），部分 Pylance 版本推断不出 `User`，访问 `.email` 报"找不到 email 字段"。

**改动**：显式标注类型，不再依赖推断链：

```python
existing_user: User | None = result.scalars().first()
```

登录契约精简后该处进一步简化为 `scalar_one_or_none()`（email 唯一，0 或 1 行），返回类型天然干净。

### 3. 认证依赖分层：激活检查上移（方案 A）

**问题**：`get_current_user` 内部既解析身份又检查 `is_active`，而 `get_current_active_user` 是纯透传空壳——职责放反，全项目 15+ 端点依赖的"激活用户"名不符实。

**改动**（`backend/app/auth/dependencies.py`）：

```python
async def get_current_user(...) -> User:
    # 只做：提取 token → 解码 JWT → 查询用户
    user = await _find_user_from_credentials(credentials, db)
    if user is None:
        raise _invalid_credentials_exception()   # 401
    return user

async def get_current_active_user(
    current_user: User = Depends(get_current_user),
) -> User:
    if not current_user.is_active:
        raise HTTPException(403, detail=INACTIVE_ACCOUNT_DETAIL)
    return current_user
```

**效果**：`get_current_user` = "登录即可"（身份真实存在）；`get_current_active_user` = "必须激活"。未来细粒度的访问控制（邮箱验证、付费状态）在后者扩展。测试同步更新：新增"get_current_user 不检查激活""active 依赖拒绝停用用户/放行激活用户"。

## 二、ORM 会话模型知识点

### 1. flush / commit / refresh 三兄弟

| 操作 | 方向 | 发什么 SQL | 效果 |
|---|---|---|---|
| `flush` | 对象 → 数据库 | INSERT/UPDATE | 把改动发出去、触发默认值生成；**未提交**，当前事务内可见，可回滚 |
| `commit` | 事务定案 | 结束事务 | 持久化、其他连接可见、无法回滚 |
| `refresh` | 数据库 → 对象 | SELECT（按主键） | 用库里的真实值覆盖内存对象 |

- Python 端 `default=`（如 `id`、`created_at`）在 **flush 那一刻**才被调用并写回对象，构造对象时属性是 `None`——所以注册流程必须 flush 后才能拿 `new_user.id` 签 JWT。
- 实测：Python 默认值字段 flush 后直接访问即有值；连 `server_default` 字段在 SQLAlchemy 2.0 + SQLite 下也被 `INSERT ... RETURNING` 自动取回，**refresh 在纯默认值模型下是防御性冗余**，仅在触发器改行、其他事务修改同行、无 `expire_on_commit=False` 时才必要。
- 本项目 `get_db`（`backend/app/database.py`）：路由正常返回 → commit；异常 → rollback → 重新抛出。service 层从不 commit。

### 2. Result 是"一次性容器"，不是数据

实测：`db.execute(select(User))` 返回 `ChunkedIteratorResult` 对象（打印只有地址）；`.all()` 取出的每个元素是 `(User,)` 元组（Row）；**第二次 `.all()` 返回 `[]`**——结果被消费一次就没了（one-shot，支持大结果集流式处理）。

```python
result = await self.db.execute(select(User))
user = result.scalar_one_or_none()   # 立刻取数，result 用完即弃
```

### 3. 标量家族速查

| 方法 | 语义 | 0 行 | ≥2 行 |
|---|---|---|---|
| `scalar_one_or_none()` | 单列标量，0 或 1 行 | `None` | 抛 `MultipleResultsFound` |
| `scalar_one()` | 单列标量，必须恰好 1 行 | 抛异常 | 抛异常 |
| `scalar()` | 单列标量，取第一条 | `None` | 取第一条 |
| `one_or_none()` | 整行 Row，0 或 1 行 | `None` | 抛异常 |
| `scalars().first()` | 标量序列第一条 | `None` | 取第一条 |

概念对照：**ORM 对象** = 一行的对象化（`User` 实例，本质就是普通 Python 对象）；**Row** = 一行原始元组；**标量** = 单个值；**标量序列（ScalarResult）** = 每行第一列拆出来的值列表。`select(User)` 的"第一列"是实体本身，所以 `scalar_one_or_none()` 返回 `User`。email 唯一索引保证 `scalar_one_or_none()` 的"≥2 行抛异常"分支永不触发，它是一道数据完整性保险。

## 三、错误处理分层架构知识点

### 1. 三种错误载体 + 四条到达客户端的路径

"客户端能接到的从来不是异常，而是 HTTP 响应"。异常是服务端进程内的东西，翻译成响应才出得去。

| 载体 | 是什么 | 谁抛 | 谁接 | 状态码 |
|---|---|---|---|---|
| 领域异常 | 自定义类（`EmailAlreadyRegisteredError` 等） | service 层 | router `except` → HTTPException | 400 |
| HTTPException | FastAPI 的类 | router / 依赖 | FastAPI 内置 handler | 401/403 等 |
| RequestValidationError | FastAPI/Pydantic 框架异常 | 框架（路由执行前） | `core/exceptions.py` 422 handler | 422 |
| 其他 Exception | 任意漏网 | 任意 | `core/exceptions.py` 500 兜底 | 500 |

```
HTTP 请求
  ├─① Pydantic 校验失败 → RequestValidationError → 422 handler → 422 JSON
  ├─② 依赖层失败（get_current_user）→ HTTPException(401) → 内置 handler → 401 JSON
  ├─③ service 业务规则失败 → 领域异常 → router except → HTTPException → 400 JSON
  └─④ 漏网之鱼 → Exception → 500 兜底 → 500 JSON
```

**关键认知**：
- **"包装成 HTTPException"不是翻译的唯一方式**——校验异常走的是"提前注册 handler，handler 直接 return JSONResponse"；HTTPException 最终也是被 FastAPI 内置 handler 转成 JSONResponse 才发出去。客户端只认"状态码 + header + body"。
- **HTTPException 不是领域异常的"最终形态"，是翻译产物**：两者独立，router 只是翻译官。`HTTPException` 是"自带翻译的异常"（内置注册），领域异常"没注册"所以 router 必须手动接住。
- **HTTPException 不会被 500 兜底吃掉**：Starlette 中间件分层，HTTPException 走自己的 handler。
- **format 函数家族只服务校验异常**：因为只有 `RequestValidationError` 的错误载荷是 Pydantic 结构化错误字典（`loc`/`type`/`msg`/`ctx`，英文机器格式），需要翻译；领域异常消息在定义处就是中文，HTTPException 的 detail 构造时就是成品，500 故意不 format（防泄漏）。
- **客户端还能收到**：429（限流中间件 `core/middleware.py:207` 主动返回）、404/405/413（Starlette 内置）、成功响应 200/201、以及超时/连接拒绝等**非 HTTP 的客户端侧失败**（前端 fetch 自己抛错，没有状态码）。

### 2. errors.py vs exceptions.py 命名

| 文件 | 职责 | 为什么叫这个 |
|---|---|---|
| `app/auth/errors.py` | 定义"错误长什么样"：领域异常类 + 用户可见消息常量 | 不止异常类，还装消息常量，"errors" 是统称 |
| `app/core/exceptions.py` | 处理"异常发生后怎么办"：注册 handler，把异常转 JSON 响应 | 管的是异常处理机制 |

分层原则：**service 层抛领域异常（HTTP 无关，可复用）；HTTP 边界（router/依赖）抛 HTTPException；core 兜底**。领域异常不携带 HTTP 概念（状态码、响应头），所以 `_invalid_credentials_exception()` 这种带 `WWW-Authenticate` 头的 401 构造器放在 dependencies.py 而非 errors.py。

## 四、本次遗留与后续建议

- **全局异常映射架构**（可选项）：若追求"所有领域异常 → HTTP 映射集中在全局 handler"，需把 router 的 try/except 整体搬迁，收益是映射集中、代价是代码跳转变远。当前"按层决定抛什么"已自洽，非必须。
- **`get_current_active_user` 未来扩展点**：邮箱验证、付费状态等细粒度访问控制在此依赖内扩展，所有受保护端点自动生效。
