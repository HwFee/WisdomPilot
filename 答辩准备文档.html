// 快速抓住重点 · 5分钟理解整个系统

智码领航 = 一个帮大学生学编程的网站。它有两个学习模式：① 按章节上课（精进之路，用BKT算法判断你学会了没）；② 自由刷题（挑战之路，用推荐算法给你推合适的题，还有游戏段位让你上瘾）。后台接入了DeepSeek等AI大模型，能自动出题、讲错题、审查代码。学生做错题会进错题本，想求助AI要消耗"智核"货币（防止抄答案）。代码提交后由Judge0沙箱执行并判分。

答辩万能话术模板

【开场白】"各位老师好，我们的作品是'智码领航'——一个基于生成式AI的高校编程教学与赛训一体化平台。我们发现传统OJ平台只有刷题功能，缺乏学习路径和个性化辅导，而静态教程又缺少交互。所以我们做了一个'双轨'平台：精进之路帮学生按章节系统学习，挑战之路让学生自由刷题并获得游戏化激励，AI贯穿全程提供个性化辅导。"

【被问到技术难点】"最核心的技术难点有两个：一是BKT算法，它是教育数据挖掘领域的经典模型，我们用贝叶斯公式把学生的知识掌握状态建模为概率，而不是简单的'会/不会'；二是混合推荐算法，融合了行为评分、向量语义相似度和难度匹配三个因子，确保推荐的题目既相关又有挑战。"

【被问到创新点】"我们的创新点在于'双轨+AI+游戏化'的三位一体设计。市面上要么只有OJ刷题（洛谷），要么只有静态教程（菜鸟教程），我们把系统化教学路径、自适应推荐、AI个性化辅导、游戏化激励整合到了一个平台里，而且BKT和段位系统完全解耦，服务不同场景。"

如果评委只问一句话，怎么答？

"你们是干什么的？"
帮大学生学编程的在线平台，有章节学习+自由刷题两种模式，AI根据学生薄弱点自动出题和辅导。
"和洛谷有什么区别？"
洛谷只有刷题，我们有学习路径（BKT评估掌握度）、AI辅导、游戏化段位，定位是教学系统不是竞赛OJ。
"AI 做什么？"
①根据薄弱点生成个性化强化题 ②分析错题给讲解 ③审查代码给优化建议 ④三级提示（方向→思路→详细解析）。
"BKT 是什么？"
贝叶斯知识追踪，把学生对一个知识点的掌握建模为概率，每次答题后用贝叶斯公式更新，不是简单的'会/不会'。
"推荐怎么做？"
三因子混合：40%历史答题行为 + 35%向量语义匹配（薄弱点相关度）+ 25%难度匹配（最近发展区），加权求和排序。
"段位是干什么的？"
游戏化激励，和BKT解耦。做对得星，做错有免费次数不扣星，有段位保护，降低挫败感，让学生愿意持续刷题。

项目概述

// 30秒版本 · 对应PPT第1页 · 建议讲1-2分钟

这是一个帮大学生学编程的网站。老师上课讲完了，学生课下做题不会、不知道练什么、错了没人讲——我们就做了这个平台来解决这些问题。它像是一个"智能编程家教"，知道你哪里不会，给你推合适的题，错了给你讲，还能用游戏段位让你刷题刷上瘾。

"智码领航"是一个基于生成式AI的高校编程教学与赛训一体化平台，支持 C/C++/Python 等多门编程语言的在线学习与练习。

系统采用双轨学习路径设计：

01
精进之路
章节闯关制学习，配备 BKT（贝叶斯知识追踪）算法评估知识掌握度，系统化课堂学习路径。
02
挑战之路
无限挑战模式，基于混合推荐算法自适应推题，搭配王者荣耀风格段位系统提供游戏化激励。

【建议话术】"我们的平台叫'智码领航'，定位是高校编程教学与赛训一体化。目前支持C、C++、Python三门课程。

系统有两个核心学习路径：一是精进之路，学生按章节闯关，我们内置了约400道精选题，学生答完后BKT算法会评估他对每个知识点的掌握程度，达到阈值就解锁下一章。二是挑战之路，无限刷题模式，系统根据学生的历史表现和薄弱知识点，用混合推荐算法自动推题，做对得星星、升段位，像王者荣耀一样有游戏化激励。

整个平台接入了DeepSeek、MiniMax等多厂商AI，可以自动给学生生成个性化强化题、分析错题、审查代码，相当于给每个学生配了一个24小时的AI助教。"

  • "你们支持什么语言？" → C、C++、Python三门课程，Judge0沙箱支持代码执行。
  • "你们用户是谁？" → 高校计算机专业学生，特别是程序设计课（挂科率最高的课之一）的在校生。
  • "你们解决了什么问题？" → 学生"上课听懂做题不会"、"不知道练什么"、"错了没人讲"、"刷题没动力"四大痛点。

第一，学生不知道练什么，OJ平台题库成千上万，新手完全不知道怎么选；第二，代码错了没人讲，老师不可能一对一辅导每个学生的每道错题；第三，刷题没动力，传统平台做对一题只有冷冰冰的Accepted，学生很容易放弃；第四，错题反复错，没有系统的错题复盘机制。

针对这四个问题，我们设计了双轨学习路径+AI辅导+游戏化激励的解决方案。精进之路帮学生按章节系统学习，挑战之路用推荐算法自适应推题，AI提供个性化辅导，段位系统提供即时成就感。"

简单说就是三层：前端是用户看到的网页（用Next.js做的，代码编辑器是VS Code同款内核）；后端是处理逻辑的（FastAPI框架，处理题目推荐、知识追踪、段位计算、AI调用）；外部服务是AI大模型（DeepSeek等）和代码执行沙箱（Judge0）。前后端通过REST API通信，AI回复是流式的（SSE）。

各层职责详解

前端层（Next.js 16 + React 19）
学生看到的界面。精进之路和挑战之路是两个核心页面，代码编辑器嵌入的是 Monaco Editor（VS Code同款），保证学生写代码的体验和专业IDE一致。数学公式用KaTeX渲染，AI回复用Markdown展示。
后端层（FastAPI + SQLAlchemy 2.0）
所有业务逻辑都在这里。BKT模块负责计算知识掌握度，推荐引擎负责挑题，段位服务负责计算星星和段位升降，AI服务层负责调用大模型API，向量匹配负责找相似题目。数据库用SQLAlchemy异步ORM操作。
外部服务层（AI + Judge0）
AI层接入了DeepSeek（OpenAI协议）、MiniMax（Anthropic协议）、Ollama（本地模型）三家，通过配置切换，不用改代码。Judge0是在线判题沙箱，学生提交的代码在这里安全执行并返回结果。

【建议话术】"我们的系统采用前后端分离的三层架构。前端用Next.js 16，代码编辑器直接嵌入Monaco Editor——就是VS Code用的那个编辑器内核，学生写代码的体验和专业开发环境一样。

后端选用FastAPI，因为它是Python生态里对异步支持最好的Web框架。我们的场景里有大量IO密集型操作——调用AI API、查数据库、执行代码沙箱——用async/await可以大幅提升并发性能。而且FastAPI基于Pydantic的类型系统和自动生成的OpenAPI文档，让前后端协作非常高效。

AI层我们没有绑定单一厂商，而是抽象了一个AIProvider基类，实现了DeepSeek、MiniMax、Ollama三个具体Provider，通过配置文件切换。这样如果某个API服务不稳定，或者部署环境没有外网，可以无缝切到本地模型。"

  • "为什么选FastAPI而不是Django/Flask？" → FastAPI原生支持异步（async/await），我们的场景有大量AI API调用和数据库IO操作，异步能大幅提升并发性能。而且FastAPI自动生成OpenAPI文档，前后端协作效率高。
  • "为什么选Next.js而不是Vue？" → Next.js 16支持服务端组件和客户端组件的混合渲染，SEO友好，而且React生态在组件库和工具链上最成熟。Monaco Editor对React的集成也最好。
  • "AI层怎么保证稳定性？" → 多厂商备份+降级方案。主用DeepSeek，如果服务异常可以切到MiniMax，如果完全没有外网可以切到Ollama本地模型。通过配置切换，零代码改动。
  • "Judge0是什么？安全吗？" → Judge0是业界成熟的在线判题沙箱，用Docker容器隔离，非root用户运行，限制CPU时间和内存。我们设置了10秒CPU和256MB内存的安全限制。

06

三大核心算法

// 对应PPT第11页 · 修正版 · 详细技术解读
修正说明：PPT原版的"三大核心算法"存在三个问题：① 遗漏了BKT这个最核心的教育算法；② "协同过滤推荐"表述不准确；③ "动态调整学习路径"是功能不是算法。以下是准确版本。

算法一：BKT（贝叶斯知识追踪）— 用于精进之路

理论来源：Corbett & Anderson, 1994，被 Khan Academy、ASSISTments、Duolingo 采用。

模型本质：隐马尔可夫模型（HMM）

BKT 的核心思想是将学生的知识掌握状态建模为一个两状态隐马尔可夫模型。学生对一个知识点的掌握状态只有两种可能：

  • 已掌握（Known / K）：学生真正理解了这个知识点
  • 未掌握（Unknown / U）：学生尚未理解这个知识点

但系统无法直接观测到这个"隐藏状态"，只能通过学生的答题行为（对/错）来推断。每次答题后，系统用贝叶斯公式更新对隐藏状态的概率估计。

核心公式推导

第一步：根据答题结果，用贝叶斯公式更新掌握概率

假设当前估计学生掌握该知识点的概率为 P(L)，学生刚刚答对了这道题：

P(L|correct) = P(L) * (1 - P(S)) / [P(L)*(1-P(S)) + (1-P(L))*P(G)]

分子：P(L) * (1-P(S))  →  学生确实掌握了 * 学生没有失误
分母：所有答对的可能性  →  真会且没失误  +  不会但猜对了

如果学生答错了：

P(L|wrong) = P(L) * P(S) / [P(L)*P(S) + (1-P(L))*(1-P(G))]

分子：P(L) * P(S)  →  学生掌握了 * 但失误了
分母：所有答错的可能性  →  真会但失误了  +  不会且没猜对

第二步：考虑"学习"的发生（状态转移）

即使学生在答题前不会这个知识点，做完这道题后也可能学会了。因此需要在观测更新后再叠加学习概率：

P(L_new) = P(L|answer) + (1 - P(L|answer)) * P(T)

解释：新的掌握概率 = 答题后估计的概率 + 剩余不会的 * 这次学会了

完整计算示例

假设某学生做一道选择题，参数为：p_l0=0.15, p_t=0.1, p_g=0.25, p_s=0.05

bkt_calculation.log
# 初始状态：学生还没做过任何题 P(L) = p_l0 = 0.15 # ===== 第1题：答对了 ===== # 贝叶斯更新（答对） P(L|correct) = 0.15 * (1-0.05) / [0.15*(1-0.05) + (1-0.15)*0.25] = 0.1425 / [0.1425 + 0.2125] = 0.1425 / 0.355 = 0.401 # 叠加学习效应 P(L_new) = 0.401 + (1-0.401) * 0.1 = 0.401 + 0.0599 = 0.461 # ===== 第2题：答错了 ===== # 当前 P(L) = 0.461 # 贝叶斯更新（答错） P(L|wrong) = 0.461 * 0.05 / [0.461*0.05 + (1-0.461)*(1-0.25)] = 0.023 / [0.023 + 0.404] = 0.023 / 0.427 = 0.054 # 叠加学习效应 P(L_new) = 0.054 + (1-0.054) * 0.1 = 0.054 + 0.095 = 0.149

关键洞察：第2题答错后，掌握度从0.461骤降到0.149。这是因为一次答错带来了强烈的"不会"信号（虽然有可能是失误，但p_s只有0.05，概率很低）。这体现了 BKT 的保守性——系统不会因为一两道题的偶然答对就判定学生掌握了。

在我们系统中的实际应用

  • 学生每答一道题，系统更新该题涉及的每个知识点的掌握概率（一道题可能涉及多个知识点）
  • 知识点掌握度 → 聚合为小节掌握度 → 章节掌握度 → 课程掌握度
  • 小节掌握度达到阈值（0.80），判定该小节"已完成"
  • 章节下所有小节完成，解锁下一章节

防刷分机制

防刷分机制：最短答题时间3秒、每小时每知识点最多50次、单次会话增长上限0.35。这些限制防止学生通过反复刷同一道简单题来快速提高掌握度。

算法二：混合推荐算法 — 用于挑战之路

挑战之路的推荐目标与精进之路不同：精进之路有固定的章节-知识点结构，BKT可以精确评估；挑战之路是开放式题库，需要用推荐算法从海量题目中挑选最适合学生当前水平的题。

三因子融合（权重固定）

final_score = 0.40 × behavior_score      (行为评分)
            + 0.35 × embedding_similarity (向量语义相似度)
            + 0.25 × difficulty_match      (ZPD难度匹配)

三个因子的权重经过调参确定，总和为1。权重分配的逻辑是：历史行为最能反映学生当前状态（40%），语义匹配保证题目与学生薄弱点的相关性（35%），难度匹配保证最近发展区的有效性（25%）。

因子一：行为评分（40%）— 基于用户历史答题模式

行为评分综合三个子指标：

behavior_score = w1 × accuracy_factor + w2 × experience_factor + w3 × trend_factor

其中：
  accuracy_factor = min(1, max(0, (user_accuracy - 0.5) / 0.4))
    → 正确率50%得0分，90%以上得1分，线性插值

  experience_factor = min(1, solved_count / 100)
    → 答题数0得0分，100题以上得1分

  trend_factor = 最近10题的正确率（滑动窗口）
  • 高正确率(>80%) → 行为评分接近1 → 倾向推荐难题
  • 低正确率(<50%) → 行为评分接近0 → 倾向推荐基础题
  • 答题次数多 → 经验丰富 → 推荐挑战题
  • 趋势因子捕捉学生最近的状态波动，避免被早期数据主导

因子二：向量语义相似度（35%）— 基于 Embedding 技术

这是推荐系统的"灵魂"——确保推荐的题目与学生真正需要练习的知识点相关。

步骤1：生成用户画像文本

系统分析学生的错题和薄弱知识点，生成一段自然语言描述：

"该学生在【循环结构】、【数组操作】知识点上表现较弱，
 在【函数定义】、【基本输入输出】知识点上表现良好。"
 → 输入 Embedding API → 1536维向量

步骤2：生成题目向量

每道题目的知识点标签同样转换成文本描述：

"本题涉及【循环结构】、【条件判断】，难度3，编程题。"
 → 输入 Embedding API → 1536维向量

步骤3：余弦相似度计算

cosine_similarity(A, B) = (A · B) / (||A|| × ||B||)
                        = Σ(Ai × Bi) / (√ΣAi² × √ΣBi²)

结果范围 [-1, 1]，我们将其归一化到 [0, 1]

相似度越高，说明这道题的考查内容与学生薄弱点越匹配。

技术细节：使用 SiliconFlow 的 BAAI/bge-large-zh-v1.5 模型生成 Embedding。该模型专为中文语义理解优化，在 C-MTEB 中文语义向量基准测试中排名前列。1536 维向量在语义空间和计算效率之间取得平衡。

因子三：ZPD难度匹配（25%）— 基于最近发展区理论

最近发展区（Zone of Proximal Development, ZPD）是维果茨基提出的教育心理学理论：学生应该做"跳一跳够得着"的题目——太难会挫败，太简单没成长。

difficulty_match = 1 - |exercise_difficulty - user_optimal_difficulty| / max_difficulty

user_optimal_difficulty 由以下规则确定：
  • 新用户（答题 < 5次）：optimal = 1
  • 初学者（答题 < 15次）：optimal = 1-2
  • 有经验（答题 ≥ 15次）：optimal = 实际平均难度 + 0.5（略高于当前水平）
  • 新用户（答题<5次）：限制在难度1，防止一开始就被难题劝退
  • 初学者（答题<15次）：限制在难度1-2，循序渐进
  • 有经验：使用传入的难度范围，允许挑战更高难度

多样性过滤

纯按分数排序会导致推荐的题目知识点高度集中（比如全是循环题）。系统在最后一步进行MMR（Maximal Marginal Relevance）多样性重排：

MMR_score = λ × relevance_score - (1-λ) × max_similarity_to_selected

λ = 0.7（更偏重相关性而非多样性）

已选入推荐列表的题目之间保持足够的知识点差异，避免学生陷入单一知识点的重复练习。

算法三：向量语义匹配 — 支撑推荐与题目检索

为什么需要向量语义匹配？

传统的关键词匹配只能处理"字面相同"的情况。例如：

  • 学生薄弱点是"循环结构"
  • 题目A标签是"for循环" → 关键词匹配命中
  • 题目B标签是"迭代遍历" → 关键词匹配漏掉，但语义上其实是同一回事

向量语义匹配通过将文本转换为高维向量，在语义空间中计算相似度，从而实现同义词、近义词、上下位词的自动关联。

Embedding 技术原理

Embedding 是将离散的文本符号映射到连续向量空间的技术。BAAI/bge-large-zh-v1.5 模型基于 Transformer 架构，通过大规模中文语料预训练，学习到词语和句子的深层语义表示。

输入文本  →  Tokenizer分词  →  Transformer编码  →  池化层  →  1536维向量
"数组排序"    [数组, 排序]      12层注意力计算      MeanPooling    [0.23, -0.15, ...]

在向量空间中，语义相近的文本距离近，语义无关的文本距离远。例如：

  • "循环结构" 与 "for语句" 的向量夹角很小（高度相似）
  • "循环结构" 与 "递归函数" 的向量夹角中等（部分相关）
  • "循环结构" 与 "文件读写" 的向量夹角很大（几乎无关）

向量存储与检索的技术实现

系统中采用以下技术栈实现高效的向量存储和检索：

  • 向量生成：SiliconFlow API（BAAI/bge-large-zh-v1.5，1536维）
  • 向量存储：SQLite 数据库中 exercises 表的 embedding_vector 字段（JSON 序列化）
  • 相似度计算：Python 中 NumPy 实现的批量余弦相似度
  • 检索优化：候选集先按难度粗筛（减少80%计算量），再对剩余题目做精确向量匹配

【建议话术】"AI在我们的系统里扮演的是'助教'角色，不是'代写'角色。具体有四个应用场景：

第一，生成强化题。学生做完基础题后，系统分析出薄弱知识点，组织成prompt发给大模型，自动生成针对性的练习题——不同学生薄弱点不同，看到的强化题也不同。

BKT 算法的理论基础是什么？你们怎么用的？

BKT 全称 Bayesian Knowledge Tracing，来自卡内基梅隆大学 Corbett 和 Anderson 1994 年的论文，是教育数据挖掘领域最经典的知识追踪模型之一，Khan Academy、ASSISTments、Duolingo 都在用。

它的核心思想是：把学生对一个知识点的掌握状态建模为概率，而不是简单的'会/不会'。每次答题后，用贝叶斯公式更新这个概率。算法有四个参数：初始掌握率 p_l0、学习率 p_t、猜测率 p_g、失误率 p_s。比如一道选择题，学生答对了，系统不会直接认为他掌握了——因为可能是猜对的（p_g=0.25）。随着答题序列积累，系统不断修正估计。

在我们系统中，BKT 只用于"精进之路"的知识掌握度评估。学生每答一题，系统更新该题涉及每个知识点的掌握概率，然后向上聚合为小节掌握度、章节掌握度、课程掌握度。当小节掌握度达到 0.80 阈值，判定该小节完成；章节下所有小节完成，解锁下一章。我们还针对不同题型设置了不同的猜测率参数。

注意：BKT 和段位系统是完全解耦的两套系统。BKT 负责教育评估，段位负责游戏化激励。

你们如何实现自适应推荐？和 BKT 是什么关系？

我们的自适应推荐用在"挑战之路"，采用三因子融合的混合推荐算法：

  1. 行为评分（40%）：分析用户历史答题模式。高正确率用户倾向推荐难题，低正确率倾向推荐基础题。
  2. 向量语义相似度（35%）：基于 Embedding 技术。将用户的薄弱知识点生成文本描述，调用 SiliconFlow 的 BAAI/bge-large-zh-v1.5 模型转成 1536 维向量；题目也做同样的向量化。用余弦相似度匹配最适合的题目。
  3. 难度匹配（25%）：基于教育心理学的最近发展区理论（ZPD），推荐略高于用户当前水平的题目。新用户限制在难度1，有经验后逐步放宽。

三因子加权求和得到最终推荐分数，再经过多样性过滤避免推荐过于相似的题目。

和 BKT 的关系：挑战之路的推荐不直接使用 BKT。BKT 主要用于精进之路的知识点掌握度追踪。挑战之路的推荐基于用户行为数据和向量匹配，因为挑战之路的题目是开放式题库，不像精进之路有固定的章节-知识点结构。两套系统服务不同的学习场景。

段位系统的设计思路是什么？怎么防止学生因挫败感放弃？

段位系统参考了王者荣耀的设计，目的是给学生提供即时的正向反馈和长期的成长目标。

星星规则：做对得基础奖励（难度1-2给1星，3-4给2星，5给3星），同时补回之前做错被扣的星。做错有免费尝试次数（难度越高免费次数越多，如难度3给5次），超出后才扣星，且扣星有上限（上限等于难度值）。这意味着学生不会因为一两道题的失败受到过大惩罚。

段位保护：高段位有降级保护次数（如钻石有1次保护），0星时触发保护不降级，保护用完后才降级。青铜段位是保底，不会继续下降。

设计意图：我们故意让做错题的代价低、做对题的回报高，配合段位保护和免费尝试机制，降低挫败感。段位系统和 BKT 解耦，即使学生在某道题上表现不好，不影响他的知识掌握度评估。

AI 生成题目怎么保证质量和与课程知识点匹配？

我们的 AI 题目生成是个性化的，不是随机生成。流程是：

  1. 系统先分析学生在基础题中的答题表现，识别出薄弱知识点和已掌握知识点
  2. 将这些知识点信息组织成结构化的 prompt，传给大模型
  3. 大模型根据 prompt 生成针对性的强化练习题

质量保证机制：

  • prompt 中明确指定了题型、难度、知识点范围，限制生成范围
  • 生成的题目经过格式校验（必须是有效的 JSON 结构）
  • 题目存入数据库时标记 source='ai_generated'，便于后续审核和迭代

流式生成优化：

  • 第一题生成后立即返回给学生，不用等待全部生成
  • 剩余题目在后台并发生成（信号量限制为3，避免触发 API 速率限制）
  • 前端通过轮询获取生成进度

由于强化题是针对个人薄弱点生成的，不同学生看到的题目不同，这本身就提高了针对性和学习效率。

和现有的 OJ 平台（如洛谷、LeetCode）有什么区别？

现有 OJ 平台的核心定位是竞赛刷题，特点是题库固定、学生自己选题、没有学习路径规划、没有个性化辅导。我们的定位是教学系统，核心差异在四点：

  1. 学习路径：OJ 没有路径，学生不知道练什么。我们有双轨路径——精进之路按章节推进（BKT评估掌握度），挑战之路自适应推荐。
  2. 知识追踪：OJ 只告诉你对/错。我们用 BKT 追踪每个知识点的掌握概率，告诉学生'你哪里不会'。
  3. AI 辅助：OJ 没有辅导功能。我们集成 AI 解析、代码审查、个性化题目生成，相当于给每个学生配了一个 24 小时助教。
  4. 激励机制：OJ 没有游戏化设计。我们有段位系统和智核货币，降低学习挫败感，提升持续学习动力。

洛谷是我们难度标注的参考（1入门到8NOI+），但我们的功能边界和 OJ 不同。

作品的延伸性和未来规划？

延伸性方面，我们的架构做了分层设计，核心算法通过服务化封装，升级替换成本低：

算法升级：当前 BKT 假设答题是独立事件，实际学习有长期依赖。教育数据挖掘领域有 DKT（Deep Knowledge Tracing）用 LSTM 建模更长序列，我们保留接口，未来可以平滑替换底层模型。

场景扩展：知识追踪 + 自适应推荐的框架不限于编程教学，可以扩展到数学、物理等理科的解题训练。当前已支持 3 门课程（C、C++、Python）。

教师端：计划开发教师数据看板，展示全班知识掌握热力图、识别共性薄弱点、预警挂科风险学生，让任课老师能基于数据调整教学重点。

本地部署：AI 层已支持 Ollama 本地模型，适合无外网环境（如中小学机房），降低了对云端 API 的依赖。

应用意义和社会价值？

从三个层面来说：

对学生：程序设计课是计算机专业挂科率最高的课程之一，核心痛点是'上课听懂、做题不会'。我们提供即时反馈（代码秒级运行）+ 个性化路径（不用自己选题）+ AI 辅导（不会时给提示而非直接给答案），降低自学门槛。

对教师：高校程序设计课常是一个大班 100+ 学生，老师不可能逐个辅导。BKT 自动追踪每个学生的知识点掌握状态，老师看 dashboard 就知道谁需要帮助、哪些知识点全班都薄弱。

对社会：编程教育正在下沉到中小学和职业教育，但优质师资分布不均。我们的系统降低了对高水平教师的依赖，支持本地模型部署，让偏远地区学生也能获得高质量的编程训练，符合国家'人工智能进课堂'和'计算思维培养'的方向。

Judge0 判题安全性怎么保证？如果断网了怎么办？

Judge0 本身是成熟的在线判题沙箱方案，采用 Docker 容器隔离，非 root 用户运行，限制 CPU 时间和内存。我们调用的是 Judge0 的公共 API（ce.judge0.com），代码和输入输出都经过 base64 编码传输，避免特殊字符注入问题。

断网场景：Judge0 是云端服务，断网确实无法判题。但我们有降级设计——选择题和填空题不依赖代码执行，前端可以直接判分；编程题在断网时给出友好提示，引导学生稍后重试。如果部署在内网环境，可以对接本地部署的 Judge0 实例。

智核收费会不会让学生不敢用？

智核的设计目的是防止过度依赖 AI，而不是限制使用。学生通过正常学习行为（答题正确、打卡、学习时长）可以稳定获得智核。挑战之路答对一题就给 3 个智核，足够换 3 次轻提示或 1 次中提示。

我们的理念是：学生应该先独立思考，确实卡住时再寻求帮助。三级提示的设计也是渐进式的——轻提示给方向，中提示给思路，深提示给详细解析。这种设计参考了教育心理学中的'支架式教学'理论，在学生需要时提供恰好足够的支持，然后逐步撤去支架。

为什么选择SQLite而不是MySQL/PostgreSQL？

建议回答："三个原因：①单文件部署，零运维成本，适合比赛演示和初期部署；②aiosqlite支持异步，配合SQLAlchemy 2.0异步ORM满足并发需求；③当前~400题规模SQLite完全胜任。未来题库增长到万级会迁移到PostgreSQL。"

第6页：三层架构设计

你们为什么选择前后端分离的模块化单体架构，而不是微服务？

建议回答："当前阶段采用模块化单体架构——所有模块在一个FastAPI进程内，通过router拆分。原因：①当前团队规模小，单体开发和部署成本低；②当前用户量和题库规模（~400题）单体完全胜任；③模块间通过标准化接口解耦，未来需要拆分时可以平滑过渡到微服务。"

前后端通信用REST API，为什么不用gRPC或GraphQL？

建议回答："REST API简单通用，浏览器天然支持，前后端协作门槛低。gRPC更适合服务间内部通信，GraphQL适合复杂查询场景。我们的API相对简单（CRUD+推荐+判题），REST足够。"

第7页：三大核心算法

🔥 BKT的四个参数（p_l0=0.15, p_t=0.1...）是你们自己调的吗？有实验验证吗？

建议回答："初始值参考了Corbett & Anderson 1994的原始论文和Khan Academy的实践。我们进行了小规模验证（约50名学生的模拟测试），但大规模参数调优还需要更多数据，这是我们后续工作。"

避坑：不要说是"大量实验得出的最优值"，除非你真的做了。

混合推荐算法里，40%/35%/25%的权重是怎么定的？能动态调整吗？

建议回答："当前是固定权重，基于经验设定。理论上可以做成用户可配置或A/B测试动态调整，但当前版本为了简化没有实现。"

向量存在SQLite里？那每次推荐都要全表扫描？性能怎么办？

建议回答："对，当前是JSON序列化后存入TEXT列，推荐时全表加载到内存计算。但有两层优化：①先按难度过滤，减少80%计算量；②400道题×1536维的计算在NumPy里不到5毫秒，用户无感知。未来题库上万后会引入FAISS索引。"

第8页：精进之路

BKT的掌握度阈值是0.80，这个值是怎么定的？如果调到0.85会怎样？

建议回答："0.80是教育领域的常见阈值，参考了Khan Academy和Duolingo的实践。调到0.85会提高解锁门槛，学生需要更多练习才能过关；调到0.75会降低门槛。当前0.80在严格性和通过率之间取得了平衡。"

学生反复做错同一道题，BKT掌握度会怎么变化？

建议回答："BKT有防刷分机制：每小时每知识点最多50次，单次会话增长上限0.35。反复做错同一题，系统会判定为'失误率'范围内的波动（p_s=0.05），但如果连续答错，贝叶斯更新会让掌握度持续下降。"

第9页：挑战之路

🔥 段位系统和BKT有什么关系？会互相影响吗？

建议回答："完全解耦，没有任何关系。BKT用于精进之路的教育评估，决定能否解锁下一章；段位用于挑战之路的游戏化激励，提供即时成就感。学生在挑战之路表现不好，不会影响他在精进之路的掌握度评估。"

避坑：这是评委最爱追问的点，一定要强调"完全解耦"。

做错题有免费次数（难度+2次），学生故意做错来刷免费次数呢？

建议回答："免费次数是为了降低挫败感，不是让学生'故意错'的。而且挑战之路做对才有智核奖励（+3/题），做错没有奖励。从经济激励上，学生倾向于做对而不是故意做错。"
